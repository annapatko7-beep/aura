## Критично — падение сервера / отказ в обслуживании

### A1. JSON-парсер не ограничивает глубину вложенности → segfault
`server/src/json.cpp`, `Parser::parseValue/parseObject/parseArray` — взаимная
рекурсия без счётчика глубины.

**Подтверждено:** пробник с входом из 100 000 вложенных `[` завершился
`Segmentation fault` (код возврата **139**). Текстовый кадр такого размера
проходит по ограничению `AURA_MAX_FRAME`, поэтому **любой подключённый клиент
роняет процесс целиком** — вместе со всеми остальными сессиями.

### A2. Склеенные фрагменты WebSocket не ограничены → исчерпание памяти
`server/src/session.cpp:151` — `fragments += frame.payload` для кадров без
флага FIN; предела на суммарный размер нет, `maxFrameBytes` проверяется только
для одного кадра.

**Подтверждено на живом сервере:** 60 кадров по 60 КБ без FIN → RSS процесса
**2548 КБ → 6024 КБ** (+3476 КБ). Память растёт почти 1:1 с объёмом данных,
ограничения нет — клиент может исчерпать память машины.

## Высокие — безопасность

### B1. `users.search` отдаёт всю таблицу пользователей вместе с email
`server/src/server.cpp` (обработчик `users.search`) передаёт `limit` из запроса
без ограничения; `ChatManager::searchUsers` возвращает `user.toJson()` —
включая `email`.

**Подтверждено на живом сервере:** запрос с `{"query": "", "limit": 1000000}`
вернул **всех** пользователей с их адресами. Любой авторизованный клиент может
выгрузить базу адресов (перебор + спам).

### B2. Нет ограничения частоты на вход и регистрацию
**Подтверждено:** поиск по `rate|throttl|attempts|brute|lockout|cooldown` в
`server/src` и `server/include` не дал ни одного совпадения. `auth.login` и
`auth.register` можно вызывать без ограничения — перебор паролей и массовая
регистрация ничем не сдерживаются.

### B3. AI-сервис по умолчанию открыт для всех
`ai/aura_ai/app.py`: `require_token` срабатывает только если задан
`service_token`, а по умолчанию он пуст; при этом CORS —
`allow_origins=["*"]`. Любой сайт может обращаться к `/v1/agent/run` и
`/v1/memory/{user_key}` напрямую, в том числе читать чужую память.

### B4. Сравнение токена не constant-time
`ai/aura_ai/app.py:92` — `x_aura_token != expected` (обычное сравнение строк).

### B5. JWT: просрочку можно обойти, заголовок не проверяется
`server/src/jwt.cpp`:
* `if (const Json* exp = ...; exp && exp->isNumber() && exp->asInt() < now)` —
  если `exp` пришёл строкой, проверка **молча пропускается** и токен считается
  бессрочным;
* заголовок не разбирается вообще: `alg` не сверяется с `HS256`;
* не проверяется, что точек в токене ровно две.

Само по себе это не даёт подделки (подпись считается всегда HMAC-SHA256 и
сверяется constant-time — вариант `alg: none` не проходит), но проверки
отсутствуют.

### B6. Публичный `server.info` раскрывает внутренности
`protocol::isPublicType` включает `server.info`; обработчик возвращает
`ai_service` (внутренний адрес AI-сервиса), полный список обработчиков,
статистику БД и число соединений — до авторизации.

## Средние — логика и протокол

### C1. `Session::close()` никогда не отправляет close-кадр
`server/src/session.cpp:180`:
```cpp
if (!alive_.exchange(false)) return;
sendRaw(ws::closeFrame(code, reason));   // sendRaw сразу выходит: !alive_
```
`sendRaw` начинается с `if (!alive_.load()) return false;`, а `alive_` уже
погашен строкой выше.

**Подтверждено:** пробник на `socketpair` — после `close(1001, "idle timeout")`
вторая сторона получила **0 байт**. Клиент видит обрыв TCP вместо корректного
закрытия 1001/1002.

### C2. `chat.read` не проверяет участие в чате
`ChatManager::markRead` — единственный метод чата без `isMember(...)`:
`history`, `members` и `send` проверку делают (это подтверждено — `chat.history`
для чужого чата вернул `forbidden`). Через `chat.read` можно проверить
существование произвольного `chat_id`.

### C3. `base64Decode`: переполнение знакового int (UB)
`server/src/crypto.cpp:273` — `buffer = (buffer << 6) | value;`, где `buffer`
имеет тип `int` и никогда не сбрасывается.

**Подтверждено UBSan:** `runtime error: left shift of 875557984 by 6 places
cannot be represented in type 'int'`. Единственное срабатывание санитайзеров на
всём прогоне тестов.

Там же: декодер принимает **и** стандартный, **и** URL-safe алфавит и
пропускает `=` в любом месте — неканонический ввод не отклоняется.

### C4. WebSocket: не проверены обязательные по RFC поля
`server/src/ws.cpp`, `decodeFrame` / `parseHandshake`:
* кадр от клиента **не обязан** быть маскированным (RFC 6455 §5.1 — сервер
  обязан закрывать соединение);
* не проверяются зарезервированные биты RSV1–3;
* control-кадры не проверяются на размер ≤125 и на запрет фрагментации;
* `Sec-WebSocket-Version` читается, но не сверяется с 13;
* `Origin` сохраняется в `Handshake`, но нигде не проверяется (CSWSH).

### C5. JSON-парсер принимает некорректные числа
`Parser::parseNumber` проверяет только `end == raw.c_str()`, поэтому хвост
молча отбрасывается.

**Подтверждено пробником:**
* `{"a": 1.2.3}` → принято, результат `{"a":1.2}`;
* `{"a": +5}` → принято, результат `{"a":5}` (ведущий `+` недопустим в JSON);
* `{"a": 0x10}` → корректно отклонено; `{"a": 1e999}` → `null` (приемлемо).

### C6. Одиночный суррогат превращается в невалидный UTF-8
`Parser::parseString` → `appendUtf8`: для кода `0xD800` без второй половины
пары пишутся 3 байта `ED A0 80` (CESU-8).

**Подтверждено пробником:** строка из 3 байт `ED A0 80`. PostgreSQL такой
текст отклоняет (`invalid byte sequence for encoding "UTF8"`), то есть запись
молча не сохранится.

### C7. Неконстантный `Json::at(index)` возвращает общий статический объект
`server/src/json.cpp`: при выходе за границы возвращается ссылка на
`static Json` — запись в неё портит данные всем потокам сразу (сервер
многопоточный). Сейчас неконстантный вариант нигде не вызывается — дефект
латентный.

### C8. `verifyPassword` доверяет итерациям из хранимой строки
`server/src/crypto.cpp` — `iterations` берётся из `pbkdf2$<n>$…` без верхней
границы: испорченная или подменённая запись в БД даёт неограниченный расход CPU
на каждую попытку входа.

## Что проверено и оказалось чистым

* **SQL-инъекций нет**: все значения передаются параметрами `$1…$n`, включая
  `LIMIT $2`; единственная конкатенация — LIKE-шаблон, он тоже параметр.
* **Пароли**: PBKDF2-HMAC-SHA256, 120 000 итераций, случайная соль 8 байт,
  сравнение `constantTimeEquals`.
* **JWT-подпись** сверяется до разбора payload и constant-time — подделка
  через `alg: none` невозможна.
* **Авторизация чатов**: `chat.history`, `chat.members`, `chat.send` проверяют
  `isMember` (подтверждено ответом `forbidden` на живом сервере); `tool.run`
  подставляет `userId` из сессии, а не из запроса.
* **QML ↔ C++**: все 24 обращения `App.*` объявлены (16 `Q_PROPERTY` + 8
  слотов), количество и порядок аргументов в вызовах совпадают с сигнатурами.
* **Python memory backend**: `user_key` используется как ключ словаря, а не
  как часть пути — обхода каталога нет; SQL-запросы параметризованы.
* **ASan/UBSan**: весь набор тестов прошёл под санитайзерами, утечек и ошибок
  памяти не выявлено (единственное срабатывание — C3).
* **Схема**: `schema.sql` применяется к PostgreSQL 16.2 без ошибок, 7 таблиц,
  ограничения `CHECK` на `kind`/`role`/`theme` на месте.

# Второй проход — то, что нашлось позже

Первый проход не покрыл `net.cpp`, `listener.cpp`, `database_embedded.cpp` и
внутренности Python-модулей. Ниже — находки оттуда.

## E1. Файловое хранилище пишется неатомарно → потеря всех данных
`server/src/database_embedded.cpp`, `flush()`:
```cpp
std::ofstream file(path_);   // сразу_TRUNCATE целевого файла
file << state_.dump(2);
```
Обрыв процесса или питание посреди записи оставляет усечённый JSON — при
следующем старте база не загружается **целиком**. Ошибки потока после записи не
проверялись.

## E2. Нет ограничения числа соединений → исчерпание потоков
`server/src/listener.cpp`, `acceptLoop()`: на каждое подключение создаётся
отдельный `std::thread` с `.detach()`, потолка нет.

**Подтверждено:** поиск по `maxConnection|limit|semaphore|RLIMIT` в `listener.cpp`,
`connectionmanager.cpp` и `config.h` не дал ни одного совпадения. Клиент,
открывший несколько тысяч соединений, исчерпывает потоки и память процесса.

## E3. `suggest_time` падает на дате без часового пояса
`ai/aura_ai/tools.py`, `_parse_dt()` возвращал **naive** `datetime` для строк
вида `2026-09-19T10:00:00`, а дальше он сравнивается/вычитается с aware
`utcnow()`.

**Подтверждено через реальный путь инструмента:**
`ToolManager().run('suggest_time', {'window': {'start': '2026-09-19T10:00:00'}}, ctx)`
→ `TypeError: can't subtract offset-naive and offset-aware datetimes`.
Аргументы приходят из `tool.run`, то есть падало по запросу клиента.

## E4. `check_calendar` падает там же
**Подтверждено:** тот же naive-вход при непустом календаре →
`TypeError: can't compare offset-naive and offset-aware datetimes`
(сравнение `e.end >= start`). При пустом календаре не воспроизводится —
поэтому тесты его не ловили.

## E5. HTTP-клиент: таймауты по операции, а не на запрос
`server/src/net.cpp`, `httpRequest()`: и `sendAll`, и цикл чтения получают
свежий `timeoutMs` на каждую операцию, поэтому суммарное время запроса ничем не
ограничено (ограничен только объём — 16 МБ). Медленный AI-сервис держит поток
обращения неограниченно долго. Там же: разбор chunked предполагает ровно
`\r\n` после тела чанка, а порт из URL не проверяется на диапазон.
