# Aura — модель безопасности

Документ описывает механизмы защиты аккаунта и данных в Aura: пароли,
сессии, токены, двухфакторную аутентификацию, шифрование секретов и журнал
событий. Все перечисленные механизмы реализованы на сервере (`server/`) и
покрыты тестами (`server/tests/test_main.cpp`, сквозной сценарий 2FA).

## 1. Пароли

- Хэш: **Argon2id** (RFC 9106), параметры `m=65536, t=3, p=4` (64 МБ, 3 прохода,
  4 потока) — победитель Password Hashing Competition, устойчив к GPU/ASIC.
- Формат: `argon2id$v=19$m=65536,t=3,p=4$<соль>$<хэш>`.
- Соль: 16 случайных байт на пользователя.
- Проверка постоянна по времени (сравнение хэшей — `constantTimeEquals`).
- Прозрачная миграция: старые хэши `pbkdf2$…` принимаются и при первом успешном
  входе пересчитываются в Argon2id.
- Политика: минимум 8 символов, обязательно буквы и цифры.

## 2. Сессии и токены

- **Access-токен**: JWT HS256, claims `sub`, `email`, `jti`, `iat`, `exp`.
  `jti` сверяется с таблицей `sessions` — выход действительно отзывает токен,
  а не только «ждёт истечения».
- **Refresh-токен**: 32 случайных байта; в БД хранится только SHA-256.
  Ротация по «семействам»: каждый обмен выпускает новый токен того же семейства
  и отзывает старый.
- **Защита от кражи refresh-токена**: повторное использование уже отозванного
  токена отзывает всё семейство и все сессии пользователя
  (событие `refresh_reuse_detected`).
- Ограничение частоты попыток входа (по адресу и по email) — защита от перебора.

## 3. Двухфакторная аутентификация (TOTP)

Второй фактор — **TOTP** (RFC 6238): одноразовые коды из
приложения-аутентификатора (Google Authenticator, 1Password, FreeOTP и др.).

Параметры (совместимы со всеми распространёнными приложениями):

| параметр | значение |
| --- | --- |
| алгоритм | HMAC-SHA1 |
| длина кода | 6 цифр |
| период | 30 секунд |
| секрет | 20 байт (160 бит), base32 |

Порядок входа: **пароль → TOTP → сессия**. Если 2FA включена, обычный
`auth.login` возвращает `requires_2fa`, после чего клиент вызывает
`auth.login2fa` с кодом.

### 3.1. Хранение секрета

- Секрет TOTP **никогда не хранится в открытом виде**: он шифруется
  **AES-256-GCM** (FIPS-197 + SP 800-38D), blob = `nonce(12) ‖ ciphertext ‖ tag(16)`.
- Ключ AES-256 (32 байта) выводится из переменной окружения `AURA_2FA_KEY`
  (SHA-256 от её значения). В демо-режиме ключ выводится из `AURA_JWT_SECRET`.
- AAD («aura-2fa-secret») связывает шифртекст с контекстом, исключая подмену.
- GCM даёт и конфиденциальность, и целостность: подделка/повреждение blob
  отклоняется по тегу.

### 3.2. Защита от повторного использования кода

Код одноразовый в пределах окна жизни. Сервер хранит `last_used_counter`
(номер последнего принятого 30-секундного окна) и отклоняет коды с номером
окна `<= last_used_counter`. Окно проверки — ±1 период (допуск рассинхрона
часов клиента). Это исключает повторный вход по перехваченному коду.

### 3.3. Резервные коды

- При включении 2FA выдаётся **10 резервных кодов** формата `XXXXX-XXXXX`
  (алфавит без визуально похожих символов 0/O/1/I/L).
- Показываются пользователю **один раз**; в БД хранится только SHA-256.
- Каждый код **одноразовый**: использованный код помечается и повторно не
  принимается.
- Резервный код принимается там же, где TOTP (`auth.login2fa`), — на случай
  потери устройства с приложением-аутентификатором.

### 3.4. Доверенные устройства

- При входе можно пометить устройство доверенным (`trust_device` + `device_id`).
- Доверие действует **90 дней** или до отзыва.
- Вход с доверенным `device_id` пропускает ввод кода (но пароль обязателен).
- Устройства можно просматривать (`devices.list`) и отзывать
  (`devices.revoke`, `devices.revokeAll`).

### 3.5. Управление

- Включение: `auth.setup2fa` (секрет + `otpauth://`-URI) → `auth.confirm2fa`
  (подтверждение кодом). До подтверждения 2FA считается выключенной — нельзя
  «включить» непроверенный секрет и потерять доступ.
- Отключение: `auth.disable2fa` **только после повторной проверки пароля**;
  удаляет секрет, резервные коды и доверенные устройства.
- Все значимые действия пишутся в журнал (см. §6).

## 4. Шифрование и хэширование (реализация)

Собственные реализации без OpenSSL (проверены эталонными векторами):

| примитив | стандарт | тест |
| --- | --- | --- |
| SHA-1, SHA-256 | FIPS 180-4 | эталонные векторы |
| HMAC-SHA1 | RFC 2104 | RFC 2202 |
| PBKDF2-HMAC-SHA256 | RFC 8018 | — |
| Argon2id | RFC 9106 | эталонный вектор |
| Base32 | RFC 4648 | RFC 4648 |
| Base64 / base64url | RFC 4648 | roundtrip |
| AES-256-GCM | FIPS 197 / SP 800-38D | KAT (Python cryptography) + roundtrip + отвержение подделок |
| TOTP | RFC 6238 | векторы RFC 6238 |

Случайность — `/dev/urandom` через `randomBytes` (секреты, токены, nonce, соли).

## 5. Журнал событий безопасности

Все значимые события пишутся в `audit_logs` (`kind`, `detail`, `remote_addr`,
время). Виды событий 2FA и входа:

- `login_ok`, `login_failed`, `login_blocked`, `login_2fa_required`,
  `login_trusted_device`
- `2fa_setup_started`, `2fa_enabled`, `2fa_confirm_failed`, `2fa_disabled`,
  `2fa_disable_failed`, `2fa_failed`, `2fa_recovery_used`, `2fa_recovery_failed`
- `2fa_device_revoked`, `2fa_devices_revoked_all`
- `password_rehashed`, `refresh_reuse_detected`, `sessions_revoked_all` и др.

Журнал доступен пользователю (экран безопасности в настройках).

## 6. Что сознательно НЕ используется

- **SMS-коды**: не используются (перехват SIM, SS7-атаки). Второй фактор —
  только TOTP/резервные коды.
- **Хранение секретов в открытом виде**: исключено (см. §3.1).
- **Жёстко заданные пароли/тестовые токены**: отсутствуют.

## 7. Passkeys / WebAuthn — исследование

Задача v3 предусматривала исследование passkeys (WebAuthn / FIDO2) как
беспарольного фактора.

**Статус: рекомендуется для версии после v1.**

Обоснование:

- WebAuthn/FIDO2 опирается на **асимметричную криптографию**: регистрация
  создаёт ключевую пару (обычно **ECDSA P-256**), сервер хранит публичный ключ
  и проверяет подпись вызова (challenge) при входе.
- Текущий крипто-слой Aura реализует симметричные и хэш-примитивы
  (SHA/HMAC/PBKDF2/Argon2/AES-GCM/TOTP), но **не содержит ECDSA P-256 и
  проверки подписей** — они требуют аккуратной реализации (или библиотеки),
  чтобы не внести уязвимости (например, через плохой nonce в ECDSA).
- Клиентская сторона WebAuthn (platform authenticator, Touch ID / Face ID /
  Windows Hello, roaming-ключи) — это отдельные API на каждой платформе
  (ASAuthorization на iOS, Credential Manager на Android, platform API на
  десктопе), что выходит за рамки текущего этапа.

**Рекомендация:** добавить WebAuthn отдельным этапом после v1, когда будет
выбрана и проверена библиотека асимметричной криптографии (или реализована и
покрыта тестами собственная ECDSA P-256). TOTP + резервные коды уже дают
надёжный второй фактор для v1 и не требуют асимметричной криптографии.

## 8. Переменные окружения, связанные с безопасностью

| переменная | назначение |
| --- | --- |
| `AURA_JWT_SECRET` | секрет подписи JWT (HS256) |
| `AURA_2FA_KEY` | ключ шифрования TOTP-секретов (AES-256-GCM); в продакшене обязателен |
| `AURA_TOKEN_TTL` | срок жизни access-токена |
| `AURA_REFRESH_TTL` | срок жизни refresh-токена |
| `AURA_MAX_LOGIN_ATTEMPTS`, `AURA_LOGIN_WINDOW` | ограничение частоты попыток входа |
| `AURA_GOOGLE_CLIENT_ID`, `AURA_GOOGLE_CLIENT_SECRET` | клиент OAuth 2.0 (Google); без них интеграции отключены |
| `AURA_GOOGLE_AUTH_URL`, `AURA_GOOGLE_TOKEN_URL`, `AURA_GOOGLE_REVOKE_URL` | эндпоинты OAuth (по умолчанию — реальные Google) |
| `AURA_GOOGLE_CALENDAR_URL`, `AURA_GOOGLE_GMAIL_URL` | базовые URL Calendar/Gmail API |
| `AURA_OAUTH_STATE_TTL` | время жизни одноразового OAuth-`state` (по умолчанию 600 с) |

## 9. Токены интеграций (этап 9)

Подключения внешних сервисов (Google Календарь, Gmail) хранят access/refresh-
токены **только зашифрованными**: AES-256-GCM, ключ — SHA-256 от
`AURA_JWT_SECRET` (или `AURA_2FA_KEY`, если задан), AAD —
`aura-integration-token` (отделяет шифртексты токенов от TOTP-секретов).

- Токены никогда не отдаются клиенту: `integrations.list` возвращает только
  метаданные (`provider`, `account`, `status`, …); поля `token_encrypted` нет
  ни в одном ответе протокола.
- OAuth 2.0 Authorization Code + **PKCE (S256)**: `code_verifier` не покидает
  сервер, `state` одноразовый (помечается использованным до обмена кода),
  TTL — `AURA_OAUTH_STATE_TTL`; повтор/чужой `state`/несовпадение провайдера
  отклоняются.
- Отзыв доступа (`integrations.revoke`) отправляет токен в Google `/revoke` и
  удаляет запись; при недоступности провайдера запись сохраняется, чтобы
  отзыв можно было повторить.
- Email из `id_token` используется только для отображения аккаунта: подпись
  не проверяется, но сам факт выдачи токена подтверждён TLS-сессией сервера
  с Google (в e2e — mock по http).

## 10. Push-уведомления (этап 13)

- **Токены устройств не покидают сервер**: `devices.push.list` возвращает
  только метаданные (`id`, `platform`, `enabled`, …); `PushDeviceRecord::toJson`
  не сериализует поле `token` — отдать его наружу нечем даже по ошибке.
- Регистрация/отзыв устройства возможны только в аутентифицированной сессии
  и только для своего пользователя: `revokeDevice` удаляет по паре
  `(user_id, id)` — чужое устройство недоступно (`not_found`).
- C++-ядро **не говорит с APNs напрямую**: нет TLS/HTTP2/ES256 в net.h и
  crypto — это сознательное решение. Сервер формирует готовый APNs-конверт
  (`url`, `headers`, `payload`) и POST-ит его во внешний шлюз
  (`AURA_PUSH_DRIVER=webhook`, `AURA_PUSH_WEBHOOK_URL`); шлюз подписывает
  JWT ключом `.p8` и форвардит запрос в Apple. Секрет подписи в ядро не
  попадает. Драйвер `dev` (по умолчанию) честно логирует вместо имитации.
- Уведомления — только для владельца: выборки фильтруются по `user_id`,
  in-app событие уходит через `deliverToUser`.
- Тихие часы и `muted_kinds` гасят только push: in-app запись сохраняется
  всегда — безопасность не зависит от настроек доставки (уведомления
  `twofactor.disabled`, `login.new` дойдут до «входящей» в любом случае).
